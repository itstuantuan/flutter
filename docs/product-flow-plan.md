# ViiTor 首版流程与接口规划

更新：2026-11-10。本文是开发规划，不表示功能已实现或后端接口已发布。

## 1. 已确认需求与当前基础

- 产品核心：用户与 AI 建立关系；AI 自主探索、与其他 AI 聊天，再向用户分享发现和经历。
- Tony 只是示例名字，不能硬编码为固定角色。后端将提供多个特征不同的 AI；目前每个用户只能拥有一个 AI。
- 用户可以查看 AI 之间的完整聊天，但该查看入口可能因排期延后。记录能力应提前设计。
- 首次探索前有可选的爱好选择；聊天中已表达的兴趣自动带入，不重复要求选择。
- 提供的图片仅表达流程，最终 UI 尚未确认，不能把图片的布局、风格或所有按钮直接视为首版需求。

当前代码已有网络请求与签名、手机号及 Google 登录实现、本地凭证保存；首页仍为登录测试页。Google 配置与后端开通需要联调，业务 token 校验和过期协议尚缺。尚无本文描述的引导、聊天、探索、社交和推送实现。

## 2. 产品流程

### 2.1 首次使用

建议顺序如下；登录位置与 AI 获取方式仍待确认。

| 步骤 | 行为与规则 | 保存内容 |
| --- | --- | --- |
| 世界观介绍 1 | 欢迎用户，介绍有性格、兴趣和故事的 AI；字幕、动态声波、静音、继续按钮 | 已完成步骤、静音偏好 |
| 世界观介绍 2 | 说明 AI 会探索、认识朋友、回来分享；介绍旁白采用独立于角色的音色 | 已完成步骤 |
| 输入姓名 | 文字输入，避免语音识别导致姓名不准确 | 用户称呼 |
| 获得 AI | 后端提供候选角色并建立唯一绑定；用户选还是系统匹配待确认 | AI 绑定关系 |
| 初次聊天 | 通过兴趣、生活等自然交流了解用户，支持先去探索；问题数量和结束条件待确认 | 会话、兴趣与相关记忆 |
| 爱好选择 | 首次探索前可选校准，已有兴趣预填，不强迫重复选择 | 兴趣选择及来源 |
| 发起探索 | 创建探索任务，展示通知邀请；不得因权限操作重复创建任务 | 任务 ID、任务状态 |
| 接收发现 | 首条发现、完整结果、发现详情；支持继续围绕发现聊天 | 发现内容、已读状态 |

通知邀请流程：应用内说明 → 用户同意后申请系统权限 → 继续探索。选择“先不用”或系统拒绝均不阻断探索。已授权不重复申请；拒绝后的再次引导时机待确认。

约 5 秒给出首条有价值反馈是体验目标，用户不必等待任务结束。原文“如果用户关闭后，再 5s 左右给出整个探索结果”中的关闭对象、计时起点及结果完成约束待确认。关闭页面与退出 App 必须区别处理；真实任务由服务端执行，不能依靠客户端倒计时保证完成。模拟版需明确标识模拟数据。

### 2.2 首次离开前的承接

首次探索回来后，AI 分享发现并提出下一次探索方向，引出遇到的其他 AI，为回访建立三种期待：陪聊、后续内容、社交经历。承接应在首次体验中自然发生，不依赖监听用户退出 App。

### 2.3 再次打开与中断恢复

| 状态 | 建议进入路径 |
| --- | --- |
| 未登录或凭证失效 | 按最终登录策略认证，保留可恢复进度；需后端提供鉴权协议 |
| 引导未完成 | 从服务端/本地状态恢复适当步骤，保留姓名和已有绑定 |
| 探索仍在进行 | 展示原任务进度，不重新发起 |
| 有未读发现 | 主体验展示未读入口，可查看结果并继续聊 |
| 引导完成且无新结果 | 日常聊天、已有发现、下一次探索计划及社交动态 |
| 点击推送启动 | 认证和状态恢复后打开对应发现/任务；目标失效时回到主体验并说明 |

不能用打开次数或账号 registered 字段判断是否需要引导。引导完成的精确判定点仍待确认，应使用独立状态。

回访图涉及 AI 广场、好友列表、其他 AI 主页、活动详情与让自己的 AI 参与活动。这些属于产品方向，首版范围需单独确认。不能默认要求首版实现全部广场和活动玩法。

### 2.4 AI 与 AI 交流

建议流程：兴趣或探索计划触发 → 服务端选择交流对象 → 创建 AI 会话 → 有限轮次交流 → 保存消息 → 生成面向用户的分享 → 必要时推送。

设置轮数、执行时长和资源限制，支持超时与失败恢复。用户私密聊天与可对外分享的兴趣/经历必须分开，不能默认将私人原文转给其他 AI。用户查看完整 AI 会话的授权范围待明确，不能据此开放所有 AI 会话。

## 3. 数据模型草案

以下为逻辑模型和建议字段，不是已确认的后端 JSON 协议。ID 使用不透明字符串，时间统一传 UTC 时间戳；字段命名、分页和枚举以最终契约为准。

| 模型 | 建议字段 | 约束 |
| --- | --- | --- |
| UserProfile | userId, displayName | 与已有账号 UID 对齐 |
| OnboardingProgress | userId, version, completedSteps, completedAt | 与账号注册状态分离，允许恢复 |
| AICharacter | aiId, name, avatarUrl, portraitUrl, description, traits, voiceId | 展示配置与服务端人设分离，不依赖固定名字 |
| UserAIBinding | userId, aiId, boundAt | 服务端保证每用户唯一；是否独占 AI 实例待确认 |
| UserInterest | interestId, label, source, updatedAt | source 区分聊天提取和手动选择；冲突覆盖规则待确认 |
| Conversation | conversationId, type, participantIds, createdAt | type 区分 user_ai 与 ai_ai；服务端控制访问 |
| Message | messageId, conversationId, senderId, content, sequence, createdAt, clientMessageId | 支持去重、稳定排序；语音字段按协议补充 |
| Memory | memoryId, ownerId, category, content, sourceMessageIds, visibility | 私密记忆与可分享信息分离，默认不公开 |
| ExplorationTask | taskId, userId, aiId, interestSnapshot, status, createdAt, updatedAt, errorCode | 状态建议 queued/running/completed/failed/cancelled；取消是否开放待确认 |
| Discovery | discoveryId, taskId, type, title, summary, content, sourceRefs, conversationId, createdAt | 内容发现和社交经历共用入口；来源可追溯 |
| DiscoveryRead | userId, discoveryId, readAt | 多端已读状态归属用户 |
| ExplorationPlan | planId, aiId, topic, status, createdAt | 下一次探索计划；不等于已自动执行的任务 |
| AIRelationship | aiId, peerAiId, summary, updatedAt | 首版先支持基础关系，复杂关系规则后置 |
| PushRegistration | installationId, userId, platform, pushToken, enabled, updatedAt | token 刷新、账号切换及退出时更新/解绑 |

通知权限属于当前设备状态，不应直接作为用户全局权限。会话记录、探索和绑定以服务端为准；本地用于缓存和恢复，按账号隔离并处理退出清理。

## 4. 接口草案与职责

下列路径仅是讨论建议，未提供、未实现，不得当作现有接口调用。业务鉴权、基础地址和响应封装需要与后端确定；现有签名 Authorization 不可直接覆盖成 Bearer。

| 建议接口 | 输入/输出要点 | 负责能力 |
| --- | --- | --- |
| GET /bootstrap | 返回用户资料、绑定、引导进度、活动任务、未读概况 | 启动恢复的统一入口 |
| PATCH /me/profile | displayName → 用户资料 | 姓名持久化 |
| PATCH /me/onboarding | 完成步骤、版本 → 权威进度 | 幂等记录进度，不允许随意跳过必要约束 |
| GET /ai/candidates | 游标/筛选待定 → AI 候选列表 | 后端提供角色 |
| POST /me/ai-binding | aiId 或匹配请求、幂等键 → 绑定 | 唯一绑定；最终取决于选择/匹配方案 |
| GET /interests | → 可选兴趣目录 | 爱好选择数据 |
| GET /me/interests；PUT /me/interests | 当前兴趣；用户选择 → 合并后兴趣 | 服务端结合聊天提取，覆盖语义需明确 |
| POST /conversations；GET /conversations/{id}/messages | 创建/获取用户会话；游标 → 消息 | 会话与历史记录 |
| POST /conversations/{id}/messages | clientMessageId、文本 → 消息及回复状态 | 去重、模型回复；流式事件协议另定 |
| POST /explorations | 兴趣/计划引用、幂等键 → taskId、状态 | 异步启动探索和必要的 AI 社交 |
| GET /explorations/{id} | → 状态、进度、已有发现、错误 | 初期可轮询；后续可接事件订阅 |
| GET /discoveries；GET /discoveries/{id} | 游标/任务过滤 → 列表；详情 | 首条发现与完整结果复用 |
| PUT /discoveries/{id}/read | → 已读状态 | 幂等标记阅读 |
| GET /me/ai/plans；GET /me/ai/friends | → 后续计划；好友摘要 | 回访内容及基础社交 |
| GET /ai-conversations/{id}/messages | 游标 → 已授权 AI 会话消息 | 查看入口可延期，服务端记录先保留 |
| PUT /push/installations/{id}；DELETE /push/installations/{id} | 平台、token、状态；解绑 | 推送登记与退出清理 |

语音识别、合成、音频上传或实时会话协议待供应方案确定。客户端不保存模型供应商秘密密钥。旁白可以使用静态音频，但资源和音色尚待提供。

通用契约必须补全：业务鉴权及过期处理、错误码、分页、请求幂等、并发冲突、超时重试、消息顺序、流式中断恢复。探索失败与部分结果需分别表达，不能把“有一条发现”等同于“任务已完成”。

推送由服务端在满足触发条件后发送，载荷建议包含事件 ID、目标类型和目标 ID，不携带私人聊天原文。推送不是结果的唯一来源：通知未送达或被拒绝时，启动查询仍能拿到结果。冷启动跳转必须等待身份和状态恢复。

## 5. 实现分层与阶段

建议按 onboarding、characters、chat、exploration、notifications 划分功能。展示层依赖流程控制与服务抽象；模拟服务和真实服务使用同一契约。沿用项目 models/ 与 json_serializable 约定，不手改生成文件。

| 阶段 | 交付 | 验收 |
| --- | --- | --- |
| A：契约与流程 | 本文、待确认决策、接口对齐 | 区分需求、假设和服务端承诺 |
| B：模拟闭环 | 占位页面、通用角色、模拟会话与任务、进度保存 | 首次到发现详情可走通，重启可恢复，明确标注模拟 |
| C：真实业务 | 资料、角色绑定、聊天、兴趣、探索、AI 社交和记录 | 使用真实后端数据；服务端继续执行离线任务 |
| D：语音与推送 | 独立旁白、语音交流、系统授权、推送与跳转 | 麦克风拒绝可文字聊天；退出 App 后收推送并直达 |
| E：联调与 UI 接入 | 异常恢复、回访验证、确认后的展示层 | 流程正确且最终 UI 验收通过 |

UI 确认后可按模块接入，不必等待 E；实际交互变化仍可能影响流程。整体工期需在接口、语音方案、首版范围和资源确认后评估。

## 6. 验收清单

- 首次、中断恢复、日常回访分流正确；姓名、绑定、兴趣与聊天不会因重启丢失，不跨账号混用。
- 连续点击、断网重试不重复绑定、发消息或创建探索；探索部分成功、失败、超时均有可恢复状态。
- 兴趣自动预填且允许校准；跳过、拒绝通知和拒绝麦克风不会让流程无法继续。
- 前台、后台、冷启动通知跳转正确；token 刷新与退出解绑正确；无推送也能通过应用查询发现。
- 首次探索后有下次计划和社交承接；未读状态正确；AI 会话记录完整、访问受控，查看入口可独立延期。

实现阶段执行适当的流程/服务测试及 flutter analyze、flutter test；修改 JSON 模型后先执行 dart run build_runner build。本次仅新增规划文档，不代表这些验收已通过。

## 7. 待确认问题

### 开发前优先确认

1. **身份与绑定**：登录在何处？候选 AI 是用户选择还是系统匹配？同一角色是否为不同用户创建独立实例？是否允许更换 AI？
2. **引导边界**：获得 AI 与姓名的最终顺序；何时算引导完成；初次聊天结束条件；跳过后回访落点。
3. **探索规则**：5 秒反馈的具体指标，“关闭”指什么；完整结果时间要求；并发任务限制、失败重试和是否允许取消。
4. **接口与供应**：业务 token 使用和校验；AI/聊天/探索后端负责人及协议；语音和推送方案、音色资源及平台范围。
5. **首版范围**：AI 好友摘要是否必做；广场、活动、其他 AI 主页做到什么程度；完整 AI 聊天查看入口是否延期。

### 接真实能力前确认

1. 爱好分类、最少选择数量（是否完全可跳过）、手动选择与自动提取冲突如何合并。
2. AI 社交触发方式、轮数和成本限制、对外可分享信息范围、用户可查看哪些 AI 会话。
3. 推送触发条件、频率、免打扰及拒绝后的提醒策略；不能将每条 AI 消息都默认推送。
4. 下一次探索是否必须由用户发起，还是允许后台自动执行；回访动态更新频率。
5. 数据保留与删除规则、多设备同步、语言及旁白文案；最终 UI 和资源交付安排。
